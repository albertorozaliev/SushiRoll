# Отчет по реализации API

## Цель работы

Было необходимо создать API для CRUD-действий ко всем таблицам проекта с использованием Django REST Framework, добавить права доступа, поиск и пагинацию.

## Что было сделано

1. Подключен Django REST Framework.
   - В `requirements.txt` добавлена зависимость `djangorestframework==3.17.1`.
   - В `config/settings.py` в `INSTALLED_APPS` добавлено приложение `rest_framework`.

2. Созданы сериализаторы для таблиц проекта.
   Файл: `restaurant/serializers.py`.

   Реализованы сериализаторы для пользователей, категорий, блюд меню, профилей пользователей, заказов, позиций заказов, оплат, избранного и отзывов.

3. Созданы ViewSet-классы для CRUD-действий.
   Файл: `restaurant/api_views.py`.

   Для каждой таблицы используется `ModelViewSet`, поэтому API поддерживает `GET`, `POST`, `PATCH`, `PUT` и `DELETE`.

4. Подключены API-маршруты.
   Файл: `restaurant/api_urls.py`.

   Основной API подключен по адресу `/api/`.

   Доступные endpoints:

   ```text
   /api/users/
   /api/categories/
   /api/menu-items/
   /api/user-profiles/
   /api/orders/
   /api/order-items/
   /api/payments/
   /api/favorites/
   /api/reviews/
   ```

5. Настроены права доступа.
   Файл: `restaurant/permissions.py`.

   Логика доступа:
   - неавторизованный пользователь не имеет доступа к API;
   - авторизованный пользователь может просматривать данные;
   - пользователь с `is_staff=True` может создавать, изменять и удалять данные.

6. Добавлен поиск по данным.
   Поиск работает через параметр `?search=текст`.

   Примеры:

   ```text
   /api/menu-items/?search=ролл
   /api/categories/?search=пицца
   /api/orders/?search=moscow
   ```

7. Добавлена пагинация.
   Файл: `restaurant/pagination.py`.

   По умолчанию на странице выводится 10 записей.

   Переключение страниц:

   ```text
   /api/categories/?page=2
   ```

   Изменение количества данных на странице:

   ```text
   /api/categories/?page_size=5
   ```

   Максимальный размер страницы ограничен 100 записями.

8. Slug больше не заполняется вручную.
   Поле `slug` убрано из пользовательских форм и отображения. Теперь оно автоматически создается из русского названия транслитерацией.

   Пример:

   ```text
   Горячие роллы -> goryachie-rolly
   Филадельфия люкс -> filadelfiya-lyuks
   ```

## Примеры проверки через Postman / Thunder Client / curl

Для чтения данных нужен обычный авторизованный пользователь:

```bash
curl -u client:pass12345 http://127.0.0.1:8000/api/categories/
```

Для создания, изменения и удаления нужен пользователь с `is_staff=True`:

```bash
curl -u manager:pass12345 -X POST http://127.0.0.1:8000/api/categories/ \
  -H "Content-Type: application/json" \
  -d "{\"name\":\"Сеты\",\"description\":\"Комбо-наборы\",\"is_active\":true}"
```

Пример поиска:

```bash
curl -u client:pass12345 "http://127.0.0.1:8000/api/menu-items/?search=ролл"
```

Пример пагинации:

```bash
curl -u client:pass12345 "http://127.0.0.1:8000/api/categories/?page=1&page_size=5"
```

## Авторизация и регистрация на сайте

Дополнительно была реализована система пользователей для сайта.

### Что добавлено

1. Страница входа:

```text
/login/
```

Вход выполняется по логину и паролю.

2. Страница регистрации:

```text
/register/
```

При регистрации пользователь сохраняется в стандартную таблицу пользователей Django в базе данных.

3. Страница профиля:

```text
/profile/
```

Если пользователь не вошел в систему, на странице профиля отображаются ссылки на вход и регистрацию.

Если пользователь вошел, отображаются:
- логин;
- email;
- имя;
- фамилия;
- роль пользователя;
- кнопка выхода.

4. Выход из аккаунта:

```text
/logout/
```

Выход выполняется через POST-запрос из формы на странице профиля.

5. Разграничение доступа в шапке сайта.

Вкладка `Данные` отображается только для пользователя с `is_staff=True`.

Обычный пользователь видит:

```text
О нас | Меню | Корзина | Профиль
```

Администратор видит:

```text
О нас | Меню | Корзина | Данные | Профиль
```

6. Администратор может создавать пользователей через раздел:

```text
/data/users/
```

При создании пользователя администратор может указать:
- логин;
- email;
- имя;
- фамилию;
- пароль;
- активность;
- права администратора сайта;
- права суперпользователя.

### Где находится логин и пароль администратора

В проекте есть команда `ensure_superuser`, которая берет данные администратора из файла `.env`.

Текущие данные:

```text
DJANGO_SUPERUSER_USERNAME=admin
DJANGO_SUPERUSER_PASSWORD=admin12345
```

То есть для входа администратором:

```text
Логин: admin
Пароль: admin12345
```

Если администратора еще нет в базе, его можно создать командой:

```bash
python manage.py ensure_superuser
```

### Связь с API

Сайт и API используют одну и ту же стандартную модель пользователей Django.

Это значит:
- пользователь, созданный через регистрацию на сайте, появляется в базе данных;
- этот же пользователь доступен через `/api/users/`;
- авторизация сайта работает через Django session auth;
- API также поддерживает session auth и basic auth.

После входа на сайт пользователь считается авторизованным и для API в рамках той же сессии.
